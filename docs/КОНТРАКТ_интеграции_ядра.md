# Контракт интеграции ядра подетального учёта

| Поле | Значение |
| --- | --- |
| От | Направление подетального учёта (`detail-accounting`) |
| Кому | Направление PSR (общий проект) |
| Дата | 14.09.2026 |
| Модель интеграции | **Импорт модулей** (решение D-181), не HTTP |
| Статус | Черновик к согласованию |

Документ фиксирует, чем направление подетального учёта делится с общим
проектом, как этим пользоваться и как менять, не ломая друг друга.

---

## 1. Модель интеграции — импорт модулей (D-181)

Общий проект использует ядро **импортируя модули `src/`** напрямую (не через
HTTP). Значит:

- зависимость идёт на **публичные функции/классы**, перечисленные ниже;
- их сигнатуры и поведение — контракт, меняются только по согласованию;
- всё, что не в списке (имена с `_`, app-слой, шаблоны), — внутреннее, может
  меняться без предупреждения, на это опираться нельзя.

Слои:
- **Общее ядро** (`src/`: парсеры, резолвер, правила, план, статус, хранилище) —
  переиспользуется обоими направлениями.
- **Приложения поверх ядра, у каждого своё:** `operator_app.py` (подетальный
  учёт), `psr_app.py` (общий PSR). Каждый правит **только свой** app-файл.

## 2. Правило изменения ядра (D-181-доп.)

Не единоличное владение, а два условия на любое изменение ядра:

1. **Аддитивность.** Новые функции/поля/таблицы — можно; менять сигнатуру или
   удалять существующее публичное — только по согласованию и с версией.
2. **Полный прогон тестов зелёный.** Любое изменение ядра проходит `pytest` по
   всему проекту (сейчас 285+ тестов). Красный прогон в `main` не мержится.

Схема БД меняется **только аддитивно** (новые таблицы/колонки + миграция в
`Storage._migrate`), чтобы не разъехаться на общей базе.

## 3. Покрытие требованиями (SR-xx)

Каждая публичная функция помечена ссылкой на требование `SR-xx` или
**«не покрыта»**. Ссылки `SR-xx` проставляет направление требований — здесь
проставлено «не покрыта» по умолчанию и указан внутренний спек-документ, если
он есть. Доля «не покрытых» велика — это функционал, построенный до/без
формального требования; список ниже и есть эта находка.

## 5. Хранилище (`storage.Storage`) — общее

БД одна, схема общая. Таблицы и владельцы:

| Таблица | Владелец | Назначение |
| --- | --- | --- |
| `details`, `order_links`, `operators`, `area_operations`, `settings` | **общее ядро** | план, связки, справочники |
| `facts`, `scan_events`, `status_outbox`, `camera_regs`, `losses` | подетальный учёт | факт, аудит, очередь 1С, камера, недостачи |
| `area_measures`, `order_area_sessions` | PSR (сосед) | натуральные измерители, сессии участков |

Правило: новые таблицы/колонки — аддитивно, миграция в `Storage._migrate`;
изменение/удаление общих таблиц (`details`, `order_links`, `operators`,
`area_operations`, `settings`) — **только по согласованию** обоих направлений.
`Storage` — единая точка доступа; бизнес-логика ходит через её методы, не в БД
напрямую.

## 6. Что НЕ публичное (опираться нельзя)

- App-слой: `operator_app.py`, `psr_app.py`, HTTP-эндпоинты, шаблоны `templates/*`
  — у каждого направления свой, меняется свободно.
- Любые функции/поля с `_` в начале.
- Внутренние детали реализации методов ядра (алгоритмы), пока сохраняется
  внешнее поведение.

## 7. Процесс совместной работы (git)

- Каждый в своей ветке; в `main` — через Pull Request с ревью.
- **Не редактировать файлы чужого направления** (app-слой, тесты чужого модуля).
- Общий `src/` core и `storage.py` — правки аддитивные, с ревью и зелёными
  тестами.
- `pull` перед `push`; **не запускать git-операции одновременно** (иначе
  `.git/index.lock` — как уже случалось). Если лок завис — удалить
  `.git/index.lock` / `.git/HEAD.lock` вручную.
- Регулярная синхронизация ветки с `main`, чтобы не расходиться.

## 8. Итог для направления требований

Все публичные функции ядра сейчас помечены **«не покрыта»** требованием SR-xx.
Это не значит, что они лишние — это значит, что функционал построен до/без
формального требования. Просьба к направлению требований: пройти по таблицам
раздела 4 и проставить `SR-xx` там, где требование есть, а остальное — оформить
как выявленный разрыв «реализация без требования» (кандидаты на до-описание
или на подтверждение задним числом).
